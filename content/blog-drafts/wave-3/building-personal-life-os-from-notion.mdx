# Building a Personal Life OS: When Notion Templates Become a Real Application

Life OS did not begin as a plan to build thirteen modules, five client surfaces, and a separate AI service. It began with a simpler frustration: personal and professional work was spread across too many tools, while the workflows that mattered most already existed in a set of Notion templates I used every week.

The useful transition was not “copy every database into code.” It was to treat those templates as evidence: they revealed the entities, relationships, views, and routines that had survived real use. I then built a self-hosted application around immediate needs, moved durable data into PostgreSQL, and kept expanding only when a new workflow earned its place.

Life OS remains experimental. It is for my own use and close friends and family while I learn which parts deserve to become focused products. It has no commercial pricing or general-user claims.

## The problem was fragmentation, not a lack of features

My personal stack included Notion, YouTube, Taskade, TV Time, n8n, and other free and paid tools. Each solved part of the problem:

- Notion held productivity, finance, and relationship systems;
- YouTube was both entertainment and a learning source;
- task and automation tools handled repeated work;
- TV tracking held years of entertainment history; and
- professional workflows needed resumes, applications, projects, and content.

The cost was context switching and disconnected data. A learning resource could not easily become a skill-tree node, scheduled practice, progress event, and reusable note. A professional project could not naturally connect its tasks, experience bullets, team history, content, and resume output. Every tool had its own identity model, export shape, limits, and subscription decision.

The product question became:

> What if I own one underlying model of my life and bring the relevant workflow to the surface where I need it?

That is different from putting every dashboard on one homepage. Consolidation should create useful relationships, not merely a crowded navigation menu.

## Why the Notion templates were valuable product research

The first working models already existed in Notion for productivity, finance, and relationships. They had accumulated edits caused by actual use: fields that were ignored, views that remained useful, recurring workarounds, and relationships I kept rebuilding manually.

Before migrating a template, I asked:

- Which records have been used recently?
- Which properties affect a decision or action?
- Which views exist only because of Notion’s constraints?
- Which formulas contain real domain rules?
- Which relationships are important enough for referential integrity?
- What must be searchable across modules?
- What should remain a flexible note rather than a typed field?
- Which recurring friction would justify custom software?

That process converts a template into a domain model. It also prevents a common mistake: reproducing the old tool’s interface instead of the user’s underlying job.

## Expand from immediate need, not feature imagination

After the first systems, new domains were added when an active problem justified them: a second brain and skill trees for learning, an indie-hacker workspace for resumes and applications, entertainment tracking, content creation, and other personal areas.

The current product covers thirteen domain areas:

| Area               | Examples of the job it supports                                           |
| ------------------ | ------------------------------------------------------------------------- |
| Game               | Paths, levels, goals, missions, progress metrics, rewards and punishments |
| Skill Trees        | Visual learning paths, node checklists, tasks, focused practice           |
| Second Brain       | Books, videos, podcasts, links, channels, areas and archive               |
| Agents             | Direct triggers and connections for cross-domain AI work                  |
| Finance            | Assets, budgets, funds, income and transactions                           |
| Productivity       | Scheduler, actions, containers and activity logs                          |
| Emotional & Mental | Journal, mood and self-awareness surfaces                                 |

The public repository also exposes an AI chat/speech area, while agents act as a cross-domain surface. Product taxonomy evolves; the important claim is the verified thirteen domain areas, not that every module has equal depth or maturity.

## A shared system of record changes what the product can do

Moving from templates to PostgreSQL was not valuable because SQL is inherently better than Notion. It was valuable because the application needed durable relationships and consistent rules across domains.

A shared account can connect:

- an activity log to a productivity action;
- that action to one or more long-term paths;
- a path to goals and missions;
- a learning resource to a skill-tree node;
- a project to tasks, experience records, collaborators, and a resume; and
- an entertainment import to a stable personal history.

Prisma provides typed access to PostgreSQL, while tRPC exposes application capabilities to the web product. Better Auth provides the identity foundation. Domain mirroring in the repository keeps each life area discoverable across pages, components, API routers, and database schema files.

This structure costs more to build than a template. It becomes worthwhile only when cross-domain behavior, automation, validation, or a specialized interface matters.

## Build the shared foundation once

Life OS is built on SaaS Forge, the open-source product foundation I created for web, desktop, and mobile SaaS delivery. Shared infrastructure includes authentication, database access, payments, CMS, email, storage, observability, and repository conventions.

That relationship produced leverage in both directions:

- Life OS could spend more effort on personal-domain features instead of rebuilding account and operational plumbing.
- Using the foundation in a large downstream product exposed upgrade conflicts and missing capabilities in SaaS Forge.

The product is available across five surfaces:

- Next.js web application;
- Electron desktop application;
- Expo mobile application;
- browser extension; and
- VS Code extension.

The goal is not to create five separate products. It is to make one data model available in the context where the workflow happens. Not every feature needs parity on every surface; the contract and identity should remain consistent even when the interface is specialized.

## Keep AI work behind a separate service boundary

Some AI tasks have Python-native dependencies, load models or large resources into memory, or take longer than an ordinary web request. FastAPI became a separate service boundary so that this work did not share the Next.js application process.

The design separates responsibilities:

```text
Web, desktop, mobile and extensions
                 |
                 v
        Next.js trust boundary
           |             |
           v             v
     PostgreSQL     signed agent request
                         |
                         v
                  FastAPI service
                         |
                         v
                    model providers
```

Calls from the web layer to the backend are HMAC-signed. This keeps the Next.js application as the public trust boundary and allows Python dependencies and model-provider logic to evolve separately.

Architecture descriptions need to match the current implementation. Earlier product plans explored longer-running LangChain and LangGraph workflows. The current public repository documents direct Python agent functions behind a synchronous signed trigger API. The service boundary still helps isolate runtime and memory concerns, but it should not be described publicly as an asynchronous job platform unless that capability is actually restored and shipped.

Current agents include YouTube knowledge capture and resume tailoring. AI capabilities remain experimental.

## The difficult work was at the seams

The hardest features were not necessarily the largest modules. They were places where two representations had to agree.

### Editable resume and PDF fidelity

An AI-assisted resume can produce good text and still fail as a product if the editor and generated PDF disagree. Different templates, pagination, line wrapping, user edits, and AI-produced sections all affect the final document. The system needed a model that could support structured editing while producing a dependable rendered artifact.

### LinkedIn authentication and publishing

Connecting an account and publishing content required careful boundaries around OAuth state, tokens, provider permissions, content state, and failure recovery. “Post this draft” is a small button on top of a multi-step integration.

### Preserving entertainment history

The entertainment system had to preserve data from a service that might become unavailable. Extracting an account history without silently dropping records became a data-engineering problem: mapping formats, deduplicating titles, retaining user state, handling partial metadata, and reconciling counts.

These examples explain why a personal system can justify custom software. The value comes from workflows and data continuity that generic tools cannot connect cleanly—not from owning another dashboard.

## A broad Life OS creates an onboarding problem

The interface makes sense to me because I used earlier Notion versions for roughly a year. I know why a field exists and how one module affects another. A new person sees thirteen domains, unfamiliar game terms, dense dashboards, and choices they have not yet earned context for.

The next design direction is progressive disclosure based on available time:

### Five-minute daily path

Offer capture, today’s smallest actions, and one progress reflection. Hide advanced configuration.

### Weekly planning path

Add schedule review, goals, finance or learning summaries, and a small number of modules chosen by the user.

### System-builder path

Reveal custom paths, formulas, agents, integrations, imports, cross-domain relationships, and advanced dashboards.

This is not merely a tutorial problem. The product should avoid asking beginners to configure the creator’s entire life model before receiving value.

## Personal usage is evidence—but limited evidence

I use most modules at least weekly and several daily. Emotional and mental, health and fitness, and miscellaneous modules are used less regularly. That observation helps prioritize product work because it comes from real workflows.

It is not evidence of product-market fit. There is no general retention cohort, customer revenue, or proof that other people want the complete system. Close friends and family usage can reveal confusing interfaces and edge cases, but it is not a substitute for a defined market test.

The commercialization strategy is therefore to avoid pricing the entire Life OS. The stronger path is to identify a focused workflow that repeatedly creates value, extract it into a beginner-friendly product, and test that product with an appropriate audience.

## A migration approach that avoids rebuilding everything at once

If you are moving from templates to a personal application, use a narrow sequence:

1. **Choose one recurring workflow.** Pick something used weekly with visible friction.
2. **Export and inventory the data.** Count records, attachments, relationships, select values, and missing fields.
3. **Define the canonical model.** Preserve identifiers and decide what remains flexible text.
4. **Build one end-to-end path.** Create, edit, search, archive, export, and recover a record.
5. **Import with reconciliation.** Compare source and destination counts and retain an error report.
6. **Run both briefly.** Confirm the new workflow is actually better before retiring the template.
7. **Add cross-domain links only when useful.** Do not create an ontology for its own sake.
8. **Keep an exit route.** Export user-owned data in understandable formats.

Treat attachments, dates, time zones, formulas, rollups, and deleted records as migration work from the beginning. They are where an apparently simple copy becomes unreliable.

## Frequently asked questions

### Is a Life OS just a large productivity app?

It can be, but the useful distinction is a shared model connecting personal domains and making workflows available across contexts. A collection of unrelated dashboards does not create that value.

### Why not keep everything in Notion?

Notion remains excellent for flexible modeling and fast iteration. Custom software becomes useful when typed relationships, specialized interaction, background automation, cross-platform clients, validation, or data ownership justify the development cost.

### Is Life OS ready for general customers?

No. It is an experimental personal product used by its builder and close friends and family. The interface needs clearer beginner paths, and several AI capabilities remain experimental.

### Does every module run on mobile, desktop, and extensions?

The product has five client surfaces that share the system, but each surface can expose the workflows suited to its context. This is not a claim of complete feature parity everywhere.

### Why use a separate FastAPI service?

It isolates Python and model dependencies, memory and runtime concerns, and provider evolution from the Next.js process. The current public implementation uses signed synchronous triggers rather than claiming a full asynchronous job system.

### Is Life OS being sold as one subscription?

No pricing is defined. The current strategy is to learn from personal use and potentially extract focused modules into smaller commercial products.

## Build from the workflows that already survived

Your existing templates are not technical debt to discard; they are field research. Start with the routine that has proven valuable, model only what it needs, and earn each new module through use.
